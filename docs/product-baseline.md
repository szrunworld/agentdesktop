# 产品基线（2026-10-07 晚，替代第三版路线的首发范围）

这份文件是各条研发线程共同引用的基线。它来自 Kevin 在 2026-10-07 晚对两份最新方案（产品策略 HTML 第 3 版、BOSS Agent 架构 HTML 及其后关于 UI-TARS 的指令）与本仓库进展的对照结论。两份 HTML 原文尚未归档进本仓库；拿到后放在 docs/strategy/ 并在此补链接。

## 首发定义

Agent Desktop 为外部 Agent 提供可创建、可观察、可操作、可停止的 desktop。多个 desktop 可以独立接收输入、并发运行，同时用户继续正常使用自己的电脑。

首批用户：已有 Agent 的开发者、电脑操作 Agent 团队、自动化测试团队。他们保留自己的模型、任务规划和业务体系，调用本产品的桌面能力。

首发集中做好：

- desktop 的创建、列举、关闭和应用绑定。
- 截图、预览、画面尺寸与坐标映射。
- 定向点击、输入、按键、滚动，以及经过验证的拖动。
- 每个 desktop 的控制权、动作顺序、停止和故障处理。
- JSON CLI、薄 MCP、连接信息和执行证据导出。
- 安装、系统权限和必要设置。

退出首发主界面：任务工作台、审批中心、模型预算界面、招聘结果管理。这些能力可以继续存在于业务 Agent 或按需使用的通用 Runtime 中。

## 八条执行规则

1. Agent Desktop 首发聚焦桌面执行工具。
2. 至少双 desktop 真并发、独立输入、宿主可用，是关键出口条件。
3. 产品资源统一为 desktop / desktopId。
4. 复用原生视觉核心与新 AI/GUI 实现，接入受管 Runtime，模型能力按需调用。
5. BOSS、微信等业务应用独立，通用能力共享，业务判断各自拥有。
6. 所有实际输入经过同一执行控制入口，每个 desktop 分别管理顺序和控制权。
7. 任务中心、审批预算等已有代码，不自动成为 Desktop 首发范围。
8. 测试通过证明对应实现；产品目标是否完成，要看该目标的直接验收证据。

## 并发语义

同一个 desktop 内的动作有序执行，不同 desktop 可以独立并发。三个概念分开：

| 概念 | 含义 | 现状 |
| --- | --- | --- |
| 一个活动协调服务 | 管理多个 desktop 的那个宿主进程 | C02（PR #66）解决其 endpoint 所有权 |
| 每个 desktop 一个写控制者 | 同一环境不被两个执行者同时操作 | 未实现，M0/M1 范围 |
| 全机只执行一个任务 | 旧路线 C05 的全局队列 | 与新目标冲突，作废；改为每个 desktop 内有序 |

## 资源语义

| 概念 | 负责表达什么 |
| --- | --- |
| Desktop / desktopId | Agent 选择的执行环境：目标绑定、观察、输入状态、动作队列、控制者 |
| Screen | Desktop 使用的底层显示资源（引擎的 `screen.*` 保留为当前底层接口） |
| 应用 Window | 应用进程拥有的窗口，由 Desktop 绑定并管理操作目标 |
| Preview Window | Agent Desktop 提供的预览入口；关闭预览不等于关闭 Desktop |

首版「一 Desktop 对应一块私有 Screen」是设计建议，最终服从后端验证结果。BOSS 架构稿里的 workspace 用词统一为 desktop，不再增加一层资源。

## 三层职责

| 层次 | 负责 |
| --- | --- |
| 桌面执行核心 | desktop 生命周期、应用与窗口绑定、观察、定向输入、坐标映射、控制权、动作回执、停止、资源释放 |
| Runtime 内的通用 Agent 能力 | 重写后的视觉请求、模型调用适配、响应解析、动作建议、按需启用的有限探索循环 |
| 业务 Agent（BOSS、微信等） | 业务目标、账号、页面策略、业务授权、任务状态、业务限额、去重、恢复、业务结果验证 |

逻辑分层，不要求新增产品或仓库。Runtime 的物理仓库归属未拍板：先拆清模块、依赖和发布边界，继续按版本复用通用实现；业务应用不得必须打开 Agent Desktop 的 UI 才能使用通用能力。

## 接入顺序

先有稳定的 JSON CLI，再用 MCP 暴露同一套桌面工具；确有调用方需要时再做 ACP 适配。采用明确的当前 Runtime 契约；不保留旧 JSONL 版本兼容义务。

| 里程碑 | 内容 | 出口 |
