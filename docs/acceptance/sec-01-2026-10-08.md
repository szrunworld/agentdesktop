# SEC-01 文件权限验收记录（2026-10-08）

要求（docs/plan/08、Kevin 2026-10-08）：
- 干净实例上，`ai.sqlite`、`runs.sqlite`、`requests.sqlite` 和各 socket 都是 0600，存放敏感数据的目录是 0700，不能只检查已有文件；
- 已有数据库要能修复权限；
- 在干净实例上验证。

## 现状与修改

- `ai.sqlite`：foundation 上已有修复（7348e58，`ConfigStore.restrictToOwner`）。打开前目录设为 0700，文件以 0600 创建，已有文件连同 -wal / -shm / -journal 一起修复。A0 子任务那次验证时这个修复还没合入，所以当时看到 0644。
- Runtime 的 `runs.sqlite` / `requests.sqlite`：原来是在 SQLite 创建文件**之后**才 chmod 主文件，有一个短暂的可读窗口；已有的 -wal / -shm 也不修复，目录权限同样不修复。本 PR 改为和 AI 配置库一样的 `restrictToOwner`：先 chmod 目录为 0700，以 O_CREAT 加 0600 创建文件并 fchmod，再修复已有的 -wal / -shm / -journal。

## 自动化测试

`swift test`：405 项全部通过，退出码 0。新增 `runtimeRecordsAreOwnerOnlyAndRepaired`：
- 新建的记录目录为 0700，两个库为 0600；
- 把目录改成 0755、所有库文件改成 0644 后重新打开，全部恢复为 0700 / 0600。

## 真机（测试副本 /tmp/adt-sec，用当前 foundation 加本 PR 构建）

| 步骤 | 结果 |
| --- | --- |
| 干净实例启动并完成一次调用 | 16 个文件和目录中，对组或其他用户开放的为 **0**。socket（runtime、ai）、锁文件、三个库及各自的 -wal / -shm、凭据文件都是 0600；记录目录、artifacts、test-credentials 都是 0700 |

| 重新启动 | 开放项 **0**：目录、三个库及其 -wal / -shm 全部恢复 |

清理：停止测试副本，删除 /tmp/adt-sec。
