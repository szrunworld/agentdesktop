# MAC-001 真机验收与 Safari 观察超时排查（2026-10-08）

结论：**MAC-001 未通过（FAILED）**。四层能力测试在真实模型上通过，但 GUI 运行未能完成中立表单。根因是**观察画面与输入目标不是同一个窗口**，属于 G0 执行边界问题，不是模型或 AI 服务的问题。上午记录的「Safari AX 观察超时」在当前构建上未复现；Runtime 在元素读取失败或变慢时只影响同一张 Desktop，不会拖住整个宿主。

## 一、观察超时排查（按「截图 / AX / 两者」与恢复能力）

| 场景 | 结果 |
| --- | --- |
| 只截图 | 0.19–0.33 s，正常 |
| 截图 + 元素（Safari 起始页 242 元素） | 1.8–2.3 s，正常 |
| 文件确认面板打开时截图 + 元素 | 2.02 s，正常 |
| 回车后立即截图 + 元素（模拟上午时机） | 1.81 s，正常 |
| 用 SIGSTOP 冻结 Runtime 启动的 Safari 后截图 + 元素 | 1.87 s 内返回 `execution_failed`（窗口不再暴露给辅助功能），没有挂起 |
| 冻结期间：`runtime status`、Desktop B 截图、Desktop A 只截图 | 0.10 s / 0.33 s / 0.26 s，都正常；宿主线程数稳定在 11 |
| SIGCONT 恢复后 Desktop A 截图 + 元素 | 2.01 s、242 元素，无需重启 |

主线程采样（观察进行中，3 s、1 ms 间隔）：主线程在事件循环空等；元素遍历在 Swift 并发任务线程上（`AgentRuntime.handle → InputEngine.state → AXSnapshot.capture → Walker.visit` 递归，每个节点一次同步 mach 消息）；Runtime 连接线程在 `RuntimeService.observe → withDesktop`（持有 Desktop 锁）里用信号量同步等待引擎。

上午 08:51 的超时：旧构建 `3884cfd`，测试副本在 08:51:03 一次 PostEvent 权限检查（已批准、立即返回，无弹框）后 50 s 无日志，08:51:53 正常退出，系统日志没有记录退出原因，没有崩溃报告。**未复现，根因未确定。**

仍然存在的风险（交 Runtime 修复）：
1. 元素遍历没有总时限：单次 AX 调用有 2 s 超时，但整棵树没有上限；目标应用响应慢（不是冻结）时，一次观察可以很久，并在此期间持有 Desktop 锁，同一 Desktop 的后续请求都会排队。
2. 引擎处理在 Swift 并发协作线程上做同步阻塞的 AX 调用；多个慢观察同时进行可能占满协作线程池，拖慢宿主里所有 async 工作（含 AI 服务）。
3. 连接线程用信号量同步等待，排队的请求每个占一个线程。

## 二、MAC-001 运行

| 步骤 | 结果 |
| --- | --- |
| 连接、模型刷新、模型配置、GUI 配置（CLI，密钥经 stdin） | 成功 |
| `ai tests start --wait` | succeeded；network / auth_model / image_input / gui_contract 全部 passed |
| 设为默认 | 成功（默认指针 r2） |
| `gui run`（goal：姓名输入 Ada 后点击应用；verification：`已保存：Ada / MAC-001-A / 提交次数 1`） | **failed**，5 步、5 次模型调用；第 5 次模型返回空回复 → `INVALID_ACTION` |
| 运行中的动作 | click (985.6, 935.1) confirmed（`event.click.overlay`）、type 3 字 confirmed（`event.unicode`）、再 click、再 type，全部回执 confirmed |
| 表单实际状态 | **没有任何变化**：姓名为空、计数 0、状态「尚未应用」 |
| 目标验证 | 每次都在较新的观察上判 failed；没有把模型自报或回执当成成功 |

根因（窗口列表证据）：Desktop A 上同一位置叠着 Safari 的三个窗口——1590「Start Page」（Runtime 绑定的目标，最下层）、1731「Untitled」、1776「Neutral · A · MAC-001-A」（表单，最上层），另有一个仍在屏上的 1734「Open」面板。按键（⌘L、输入、回车）按进程投递，Safari 因此开出新窗口并在新窗口里加载了表单。之后：

- 截图按 **屏幕** 拍，模型看到的是最上层的表单；
- 元素读取和输入都对准 **绑定窗口 1590**（被盖住的起始页）。

模型按表单坐标点击姓名框，输入送到了下面的起始页；回执的 confirmed 只证明送达了 1590；验证读的也是 1590 的元素，所以永远不会通过。这违反 DEV-SPEC §06.5 / §08.3 的目标身份一致要求：**交给模型的画面必须是将要接收输入的那个窗口。**

## 三、建议的修复（交 Runtime 负责人）

1. **观察只取绑定窗口**：截图按窗口（或按绑定窗口裁剪并确认其在最上层、未被遮挡），被遮挡时返回 `STALE_OBSERVATION`/`DESKTOP_BUSY` 而不是交出别的窗口的画面。
2. **输入前复核前台窗口**：绑定窗口不是该 Desktop 最上层窗口时拒绝输入（或先把它提到最上层并重新观察）。
3. **按键只投给绑定窗口**；做不到时在能力里如实声明，并在出现新窗口时让 binding 失效。
4. **元素遍历加总截止时间**，超时返回部分树并标 `truncated`；锁等待受请求 deadline 约束；同步 AX 不放在协作线程池上。
5. （AI 侧，我来做）模型空回复目前直接终止运行；规格允许「按明确策略重新观察后结束」，可改为计一次失败尝试后在步内重试，仍受每步 2 次上限约束。
