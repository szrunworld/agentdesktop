新增 `RuntimeIdentityTests`（10 项）：
- 正常配对：未配对时只能配对；App 不能自己批准自己；授权只能是申请范围的子集；凭据只发给发起配对的连接，且只发一次；owner 也看不到 token；配对后按 grant 生效，其余默认拒绝（`owner_only`）；数据库只存哈希。
- 拒绝配对：不发凭据、不建 client；拒绝后不能再批准；未知 capability 由 contract 拒绝。
- 错误 / 借用凭据：随便编的 token、不存在的 client、拿 B 的 id 配猜测的 token、空 token、冒充 owner，全部在握手阶段被拒绝，审计里记录声称的 clientId。
- 冒充：B 拿 A 的 Desktop、session、snapshot、Run、requestId，或在 params / context 里自报 clientId，结果都是 `not_found` 或 `schema_invalid`；同一个 requestId 对 B 而言是 B 自己的请求；列表互相隔离；只有 A 自己的点击被发出；审计记录真实调用方（B）和 runId，reason 为 `foreign_session`。
- grant 外的 App / Desktop：`grant_missing` / `not_found`，平台没有任何调用。
- 过期：`grant_expired`；续期超过 7 天由 contract 拒绝；续期后恢复。
- 撤销：policyEpoch 增加；同一连接上向已有 Run 发的动作、单次动作、读取都返回 `client_revoked`；Run 以 `client_revoked` 结束；旧凭据握手被拒；它的 session 被关闭，owner 可以销毁它的 Desktop；重新配对得到新的 clientId。
- 收窄 / 撤销 grant：超出新范围的 Run 以 `grant_narrowed` 结束；撤销 grant 后返回 `grant_missing`。
- 断连：Delegated Run 以 `owner_lost` 结束，未知动作保持 `unknown`（outcome 为 unknown）；同一 App 用同一凭据重连、用同一 requestId 重试，得到 `action_delivery_unknown`，平台不会重发。

SDK 实机测试（`SDKLiveTests`，Python 与 TypeScript 各一项）：先确认未配对时返回 `pairing_required`，再通过 SDK 的 `pair()` 配对（测试 harness 扮演 owner，通过 runtime/1 的 `hub.pairing.approve` 批准），然后以 paired 身份完成创建 Desktop、启动、绑定、观察、点击、幂等重放、过期快照的整个流程。MCP harness 也改为以 paired App 身份连接。

验收中发现并修复了两个问题，修复后在新的副本 `/tmp/adt-a4b` 上复验：
- `session exec` 在 App 被撤销后打印的是启动时的 Run 快照（phase 显示 running）。现在会如实返回 `client_revoked`，退出码 4，stderr 说明这个 Run 已被 Runtime 停止。
- 被撤销 App 的 session 仍然打开，导致 owner 无法销毁 Desktop（conflict，有 4 个 open session）。现在撤销时会关闭它的所有 session；复验中 owner `desktop destroy` 成功，计算器随 Desktop 一起退出。

收尾：两个副本都已 SIGTERM 退出，`/tmp/adt-a4`、`/tmp/adt-a4b` 已删除。第一轮里由于销毁 Desktop 失败，留下了一个计算器实例（验收时用 `--new-instance` 新开的），已手动结束。

## 接入影响

- 外部 App（ACP bridge、BOSS Agent、WeChat Agent、MCP 宿主）在合入后必须先配对，否则除配对以外的所有调用都会返回 `pairing_required`。ACP bridge 目前不带凭据，需要单独提一个 PR 接入（`--credential-file`）。
- `session exec` 的子进程继承启动者的凭据文件（通过 `AGENTDESKTOP_CREDENTIAL_FILE`）；Python / TypeScript SDK 能读取 owner 文件的裸 token 格式。
